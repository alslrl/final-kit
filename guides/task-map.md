# 과제 지도 안내 (메인이 시작할 때, 또는 내가 "과제 지도"라고 할 때 읽는다)

- README와 데이터를 읽고(메인은 서브에이전트 결과를 모아) docs/TASK_MAP.md를 만든다.
- 목적은 내가 처음 읽고 과제의 큰 그림을 이해하는 것이다. 길어도 된다(100줄 안팎). 대신 처음 보는 사람이 위에서 아래로 읽으며 이해할 수 있게 쓴다.
- 쉬운 말로 쓰고, 업무 용어나 열 이름은 처음 나올 때 한 줄로 풀어 쓴다.
- 글자로 그린 화살표 그림(ASCII 도식)은 쓰지 않는다. 미리보기 창 폭에 따라 줄이 꺾여 읽을 수 없다. 흐름은 번호 목록, 비교는 표로 쓴다.
- 파일은 실제 경로·이름 그대로 쓴다. 열 이름 전체 목록, 빈칸·중복 집계, 파일:줄 출처는 넣지 않는다(요구사항 표와 인터뷰 몫이다). 원본 행 전체를 출력하지 않는다.
- README에 없는 내용을 지어내지 않는다. 추정은 "(추정)"이라고 붙인다.
- 내가 "내가 이해한 건 이거야"라며 요약을 보내면, 틀리거나 빠진 부분만 짧게 짚는다.

```markdown
# 과제 지도

## 1. 한 문장
누가 / 무엇 때문에 힘들어서 / 무엇을 만드는가

## 2. 지금 상황
- 담당 부서와 사람들이 지금 이 일을 어떻게 하고 있나 (2~4줄)
- 무엇이 불편하거나 자주 틀리나

## 3. 만들어야 하는 것
- 사용자별로 무엇을 할 수 있어야 하나 (예: 관리자는 …, 점검자는 …)
- 꼭 내야 하는 산출물과 형식 (화면, 파일, 문서)

## 4. 주어진 자료
| 파일 | 무엇인가 | 행 수 | 한 행은 | 어디에 쓰이나 |
|---|---|---|---|---|
| data/파일.csv | 쉬운 이름 | n | 무엇 하나 | 처리 흐름의 몇 번 단계 |
- 파일끼리 이어지는 열: 파일 A의 열 = 파일 B의 열 (무엇으로 이어지는지 쉬운 말로)
- 이미 있는 코드·폴더가 있으면 무엇이 준비돼 있고 무엇이 비었는지

## 5. 처리 흐름
1. 무엇을 보고 무엇을 정하나 (쓰는 파일)
2. …
3. 결과가 어디에 어떻게 보이나

## 6. 예시 한 건으로 보면
흐름을 실제 값 하나로 따라가 본다. 내가 흐름을 제대로 이해했는지 확인하는 용도다. 3~5줄, 문장으로 쓴다.

## 7. 아직 모르는 것과 어려운 곳
- 결과를 틀리기 쉬운 곳, 담당자에게 물어야 하는 것 (5개 이하). 물을 것은 docs/QUESTIONS.md에도 올린다.

## 8. 제출과 평가
- 제출해야 하는 것, README에 적힌 평가·확인 방법
```
