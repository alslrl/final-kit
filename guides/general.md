# 범용 흐름 (과제 유형 G: 서비스 구축형 흐름이 맞지 않을 때)

메인이 과제 유형을 G로 판단하고 내가 확정하면 메인은 이 파일을 따른다. AGENTS.md의 "요구사항", "계획", "확인" 절 중 묶음·PLAN 교차 확인·verify 명령 절차는 쓰지 않는다. "공통", "세션과 역할", "원장", "소통", "결정", "시간", "커밋" 절은 그대로 지킨다.

## 1. 목표와 완료 기준 (메인)
- 과제가 요구하는 것을 한 문장으로 쓰고, 완료 기준을 3~7개로 REQUIREMENTS.md 표에 적는다. 줄마다 출처(파일:줄)와 확인 방법(재계산 / 실행 / 내가 봄)을 쓴다.
- 산출물(파일, 보고서, 코드, 답안, 발표 자료 등)의 이름과 형식을 과제 문서에 적힌 그대로 적는다.
- 나에게 보여 주고 확인받는다. 애매한 것은 ops/OPEN.md에 적고, 담당자가 있으면 interview 세션으로 묻는다.

## 2. 계획 (메인)
- 단계를 3~7개로 나눈다. 단계마다: 무엇을 / 산출물 / 누가(메인 직접, 메인의 서브에이전트, 다른 세션) / 끝났다고 보는 기준.
- 서로 기다리지 않는 단계는 서브에이전트나 세션으로 병렬 처리한다. 세션이 필요하면 역할 카드 중에서 고르고, 맞는 카드가 없으면 build 카드를 쓰되 맡을 단계와 고칠 파일을 첫 문장에 적는다.
- 계획을 ops/STATE.md에 적고 나에게 보여 준 뒤 멈춘다. 내가 승인하면 ops/DECISIONS.md에 남긴다.

## 3. 실행
- 단계마다 산출물을 파일로 남기고 ops/STATE.md를 고친다. 계산·집계는 코드로 하고 결과 파일을 남긴다.
- 막히거나 방향을 바꿔야 하면 같은 방법을 반복하지 말고 나에게 선택지 2~3개와 추천을 보여 준다.
- 모르는 개념·배경이 필요하면 docs/QUESTIONS.md에 적고 research 세션에 맡긴다.

## 4. 확인
- 완료 기준마다 확인 방법을 실행해 상태(PASS / FAIL / NOT_RUN / HUMAN_CHECK)를 표에 적는다. 숫자는 원본에서 따로 다시 계산한다.
- 확인이 무거우면 verify 세션에 "완료 기준 <번호> 확인"을 보내 맡긴다.

## 5. 마무리 (15:00부터)
- 결과 요약: 무엇을 했나 / 핵심 결과(숫자와 출처 파일) / 근거 / 한계와 다음 단계.
- 제출 문서·발표 원고·서술형 대비는 AGENTS.md 규칙대로 docs 세션(없으면 메인)이 한다.
